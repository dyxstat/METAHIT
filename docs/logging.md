# Logging and provenance

Every `./metahict run` invocation receives an immutable UTC run identifier.
Successful, failed, and resumed attempts are retained separately rather than
overwriting one log.

## Where to look first

For `--outdir results`, use these stable paths:

| Question | File |
| --- | --- |
| What is happening now? | `results/nextflow_reports/run.log` |
| Which task failed? | `results/nextflow_reports/failure_summary.txt` |
| What did each task request and do? | `results/nextflow_reports/trace.txt` |
| Where are one task's stdout/stderr? | `results/nextflow_reports/process_logs/index.tsv` |
| What parameters and software were used? | `parameters.json`, `provenance.json`, `software_versions.tsv` |
| How long did tasks take? | `report.html` and `timeline.html` |

Monitor a running workflow from another terminal:

```bash
tail -f results/nextflow_reports/run.log
```

## Directory layout

```text
results/nextflow_reports/
├── latest -> runs/20260829T143015Z
├── run.log -> latest/run.log
├── report.html -> latest/report.html
├── timeline.html -> latest/timeline.html
├── trace.txt -> latest/trace.txt
├── dag.html -> latest/dag.html
├── process_logs -> latest/process_logs
└── runs/
    └── 20260829T143015Z/
        ├── run.log
        ├── parameters.json
        ├── provenance.json
        ├── software_versions.tsv
        ├── environment_locks.tsv
        ├── samplesheet.sha256
        ├── configuration.sha256
        ├── nextflow.log
        ├── report.html
        ├── timeline.html
        ├── trace.txt
        ├── dag.html
        ├── failure_summary.txt        # failed runs only
        └── process_logs/
            ├── index.tsv
            └── 0001-PROCESS_NAME-HASH/
                ├── command.sh
                ├── command.out
                ├── command.err
                ├── command.log
                └── exitcode
```

Top-level links select the newest invocation. Files below `runs/<RUN_ID>/`
are the permanent record and are never overwritten. A second run in the same
UTC second receives a numeric suffix. Use different output or report roots
for simultaneous workflows so their `latest` links do not compete.

`--report-dir /absolute/path` places this structure somewhere other than the
output root.

## What each run-level file means

### `run.log`

The human-readable record. It contains the run ID, exact Nextflow command,
environment/database preflight, live Nextflow messages, and final status. A
normal run summarizes successful preflight checks in one or two lines. Add
`--verbose-preflight` only when individual lock checks are needed.

### `parameters.json`

The parsed CLI arguments and resolved output, work, and report paths. It also
stores the Nextflow command as an argument vector, avoiding ambiguity from
shell quoting.

### `provenance.json`

The METAHICT and Nextflow versions, Git revision when available, host,
platform, execution mode, selected entry, input/configuration checksums,
start and finish time, duration, status, and exit code. A resumed run also
records the preceding run selected by `latest`.

### `software_versions.tsv` and `environment_locks.tsv`

The first lists the versions represented by the exact Conda locks and
separately pinned dependencies. The second records environment prefixes, lock
files, and lock SHA-256 values. Together they document the runtime that was
validated before execution.

### Nextflow reports

- `report.html`: task status, duration, CPU, memory, and I/O summaries;
- `timeline.html`: task timing and overlap;
- `trace.txt`: one tab-separated row per task, including status, hash, CPUs,
  memory, duration, and work directory;
- `dag.html`: workflow dependency graph; and
- `nextflow.log`: detailed workflow-engine messages.

The HTML reports can be copied to a local computer and opened in a browser;
they do not require the workflow to remain running.

## Process-level logs

After Nextflow exits, METAHICT copies available task files from the hashed
work directory into `process_logs/`. Use `index.tsv` to map a process name and
hash to its archived directory.

| File | Meaning |
| --- | --- |
| `command.sh` | Exact task script generated by Nextflow |
| `command.out` | Standard output |
| `command.err` | Standard error |
| `command.log` | Combined process log when Nextflow produced one |
| `exitcode` | Numeric exit status |

For a process that is still running, Nextflow prints a hash such as
`[9d/68d62c]`. Locate its live directory and follow its log:

```bash
find results/nextflow_work/9d -maxdepth 1 -type d -name '68d62c*'
tail -f results/nextflow_work/9d/68d62cFULLHASH/.command.log
```

Replace `68d62cFULLHASH` with the directory printed by the first command.

## Resource records

CPU and memory allocations for each task are recorded in
`results/nextflow_reports/trace.txt`. Its `cpus` and `memory` columns show the
effective allocation, while `%cpu`, `peak_rss`, and `peak_vmem` report observed
resource use when Nextflow can collect it.

## Failure and resume records

A failed invocation receives `failure_summary.txt` when task information is
available. It lists the exit code, failed task names, archived log directories,
and original work directories.

After correcting the cause, repeat the same command and add `--resume`:

```bash
./metahict run \
  --samplesheet samplesheet.csv \
  --config metahict_configuration.yaml \
  --outdir results \
  --resume
```

The resumed attempt receives a new run ID while compatible successful tasks
are reused from `nextflow_work/`. Preserve that directory until the resumed
run finishes.
An abrupt `kill -9` can prevent final archiving; in that case the live
`.command.*` files remain in the work directory.

## What to retain for a publication

Keep at least:

- the samplesheet and configuration used for the run;
- the complete immutable `nextflow_reports/runs/<RUN_ID>/` directory;
- primary scientific results; and
- the code release/tag or source revision.

The samplesheet checksum does not include a copy of the reads. Preserve the
read-data accession, transfer checksums, and sample-to-library metadata in the
project's data-management records.

For error-specific instructions, continue to
[Troubleshooting](troubleshooting.md).
